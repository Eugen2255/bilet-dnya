# Билет дня

Telegram-бот для подготовки группы к экзамену. Бот публикует общий билет по расписанию. В личке студент отвечает на вопросы своей порции и получает проверку по утверждённому эталону. Вечером группа видит сводку. Слабые билеты возвращаются в следующих порциях.

- [Задачи команды](docs/backlog.md) — владельцы, зависимости и первый сквозной сценарий.

Контракты, алгоритмы и критерии приёмки описаны в отдельном документе «Архитектура и ТЗ — Билет дня».

`/health` проверяет процесс API. PostgreSQL проверяется отдельным healthcheck в Compose. Схема и демонстрационные данные лежат в `db/`. Контейнеры API и воркера используют один образ.

## Локальный запуск

Если локального `.env` ещё нет, скопируйте `.env.example` в `.env`. Добавьте недостающие параметры из примера в уже существующий файл. Затем выполните в корне проекта с запущенным Docker Engine.

```sh
docker compose up --build -d
docker compose ps
```

Откройте [проверку API](http://127.0.0.1:8000/health) и [OpenAPI](http://127.0.0.1:8000/docs). PostgreSQL доступен с хоста на `127.0.0.1:5433`, из Compose — на `db:5432`. `docker compose down` останавливает сервисы с сохранением локальной БД.

### Миграции и тестовые данные

После запуска PostgreSQL примените схему. Вторая команда добавляет синтетический курс в локальную БД.

```sh
docker compose exec -T db sh -c 'exec psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /db/migrate.sql'
docker compose exec -T db sh -c 'exec psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /db/seed.sql'
```

Обе команды можно повторять. `db/migrate.sql` регистрирует применённые версии в `schema_migrations`. Для изменения схемы добавляйте новый SQL-файл и шаг в `db/migrate.sql`. `db/seed.sql` заполняет только отсутствующие тестовые записи и не перезаписывает уже созданный курс.

Тестовый курс «Тестовый курс по базам данных» содержит три билета с утверждёнными рубриками, организатора и студента. Их тестовые Telegram ID указаны в `db/seed.sql`. Для общей фикстуры используйте билет №1 «Что такое первичный ключ?» и учебную дату `2035-01-20`. Учебный день и задания создаёт планировщик из CORE-02.

В схеме `assignments.group_id` связывает участника с группой курса. Закреплённая версия рубрики хранится в `assignments.rubric_id`. Балл в `attempts.result.score` хранится как целое число от 0 до 5. При создании курса достаточно группы и названия. Активация проверяет расписание, дату экзамена и утверждённую рубрику каждого билета.

После загрузки тестового курса проверьте ограничения на локальной БД. Скрипт откатывает свои изменения.

```sh
docker compose exec -T db sh -c 'exec psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /db/tests/core_01.sql'
```

### Воркер и расписание

Сервис `worker` стартует вместе с API. Он повторяет подключение, пока применяются миграции. Проверьте его через `docker compose ps` и `docker compose logs worker`. С заполненным `MODEL_PRIMARY_URL` и `MODEL_PRIMARY_ID` воркер также разбирает очередь оценок. По умолчанию он выполняет до двух проверок параллельно на процесс.

Планировщик сохраняет задания `morning:{courseId}:{day}` и `digest:{courseId}:{day}` для учебных дат в часовом поясе курса. Повторный запуск подхватывает незавершённую работу после истечения аренды. Группа получает общий билет, а каждому студенту назначается своя порция. Утренние сообщения можно отправить до вечернего среза, а сообщение со сводкой — до местной полуночи. Ответы, проверенные после времени среза, сохраняются в личной истории.

#### Задания доставки для TG-02

Все три типа содержат `courseId`, `groupDayId`, `day`, `chatId` и `expiresAt`. ID объявлены UUID, `day` — локальная дата YYYY-MM-DD, `expiresAt` — timestamp ISO 8601 с часовым поясом. Перед отправкой сверяйте срок, состояние курса и доступность адресата.

| Тип | Действие |
| --- | --- |
| `deliver_morning` | Публикация вопроса из `group_days.ticket_id` в групповой чат. |
| `deliver_daily_portion` | Сообщение в личку при известном `dm_chat_id`. Воркер загружает открытые задания по `courseId`, `memberId` и `day`. |
| `deliver_digest` | Публикация из `group_days.summary`. Срез содержит `asOf`, `active`, `responded`, `graded` и `meanScore`. При отсутствии проверенных ответов `meanScore` равен `null`. |

Воркер доставляет билеты, оценки и сводки в Telegram.

### Персональные порции, повторы и рейтинг

Миграция `003_practice` добавляет дневные порции и цепочки повторов. Сначала выдаются просроченные повторы, затем билеты с нулём и одним проходом. Общий билет получает приоритет среди билетов с тем же числом проходов. Цель считается из недостающих проходов и оставшихся учебных дат, с лимитом 8 заданий на день. Прогноз учитывает недоступные эталоны и доступные учебные даты. Один билет засчитывается не более двух раз за разные учебные даты.

Оценка ниже 3 создаёт личный повтор через два календарных дня, перенесённый на ближайшую учебную дату. Повтор для группы создаётся при среднем балле ниже 3 по минимум трём ответам на билет. Второй повтор назначается через семь календарных дней от фактической выдачи первого. В день экзамена выдача прекращается. Студент, который подключился после утра, получает порцию той же даты при первом открытии.

Рейтинг включается командой `/rating on`, скрывается через `/rating off`. Порядок определяется числом учебных дней с участием, средним баллом и псевдонимом. При публикации воркер проверяет актуальное согласие. В `group_days.summary.topics` хранятся темы, счётчики пропущенных пунктов и число фактических ошибок при достаточной выборке. Эти данные предназначены для AI-04.

Функция `app.progress.read_dashboard(cursor, course_id, member_id, as_of=None)` читает карту участника и данные группы для организатора или преподавателя. Маршрут Mini App передаёт ID членства из серверной сессии. Функция возвращает `None` вне группы.

### Подключение тестового Telegram-бота

1. Задайте `TELEGRAM_BOT_TOKEN` и отдельный случайный `TELEGRAM_WEBHOOK_SECRET` в локальном `.env`. Для секрета подойдёт вывод `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
2. Поднимите API, воркер и PostgreSQL. Примените миграции и опубликуйте API по HTTPS. Команда ниже меняет webhook бота, чей токен задан в `.env`. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook)

   ```sh
   python -m app.telegram https://your-host.example/telegram/webhook
   ```

3. Добавьте бота администратором в тестовую группу. От своего аккаунта администратора отправьте `/bind` или `/bind@имя_бота` и откройте «Подтвердить привязку» в личке. Персональная ссылка действует 15 минут и используется один раз. [Telegram Bot API](https://core.telegram.org/bots/api#getchatmember)
4. Участник группы открывает «Ответить» и нажимает Start. Ссылка в сообщении о подключении группы действует сутки. При переходе бот проверяет текущее членство и сохраняет ID личного чата. [Telegram Deep Linking](https://core.telegram.org/bots/features#deep-linking)

Webhook сохраняет событие и ставит `telegram_update:{updateId}` в одной транзакции. Воркер обрабатывает событие, ставит ответы в очередь и очищает исходный payload. Кнопка «Ответить» в утреннем посте действует до местной полуночи.

### Telegram Mini App

После настройки бота задайте `MINI_APP_URL=https://your-host.example/app/` и примените миграцию `006_miniapp` через `db/migrate.sql`. Прокси должен направлять `/app/`, `/v1/` и `/telegram/webhook` в сервис API на одном HTTPS-хосте. API проверяет данные входа Telegram с помощью `TELEGRAM_BOT_TOKEN`. При заданном `TELEGRAM_BOT_USERNAME` воркер использует его для формирования ссылок. [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)

1. После привязки и подключения группы отправьте `/app` в личном чате с ботом и нажмите «Открыть Билет дня».
2. Организатор создаёт курс, задаёт расписание, загружает вопросы и материалы, утверждает эталоны и запускает тренировку. Для приглашения преподавателя организатор выбирает подключённого участника группы и передаёт ему персональную одноразовую ссылку.
3. Преподаватель может готовить вопросы и эталоны. Студент видит свою карту билетов и разбор своих попыток. Организатор и преподаватель видят групповые показатели.

API раздаёт готовый `app.js`. После правки `app.ts` обновите его из корня проекта.

```sh
pnpm --package=typescript@5.9.3 dlx tsc app/miniapp/static/app.ts --target ES2022 --module ES2022 --strict --noEmitOnError
```

### Проверка билета в личке

После утренней публикации участник нажимает «Ответить» и выбирает билет. Ответьте на сообщение с вопросом текстом до 1000 знаков. Бот принимает одну попытку на задание и сохраняет её вместе с `grade:{attemptId}`. В личку придут балл, разбор и доступный эталон. Если через 25 секунд проверка ещё идёт, бот сообщит о задержке. Через `/today` можно открыть порцию или снова запросить результат, в том числе после неудачной доставки. Если проверка завершилась ошибкой, кнопка «Повторить проверку» запускает то же задание.

При Telegram `429` отправка откладывается на время из `retry_after`. Если после отправки результат неизвестен, задание получает `delivery_unknown`. Для группового поста оператор проверяет чат перед ручной повторной отправкой.

### Апелляции и жалобы

После оценки студент может один раз нажать «Оспорить оценку» в течение 24 часов. Воркер повторно проверяет ответ по закреплённой версии эталона. Для модели апелляции задайте `MODEL_REVIEW_ID` на основном endpoint. По умолчанию используется `MODEL_PRIMARY_ID`. Действующий балл появляется в личке и Mini App. Исходный результат сохраняется, а сводка использует оценку на момент среза.

Кнопка «Пожаловаться на эталон» доступна автору проверенного ответа. Три разных студента приостанавливают конкретную версию. В Mini App редактор увидит пометку об отзыве и может утвердить исправленный эталон. Открытые задания без ответа, отозванные сегодня, снова станут доступны с исправленным эталоном до конца учебной даты.

## Работа в команде

### Проверка модели AI-01

В локальном `.env` задайте URL Open WebUI и ключ аккаунта. Для `MODEL_PRIMARY_URL` укажите полный endpoint, например `https://openwebui.example.edu/api/chat/completions`. Если администратор разрешил маршруты с префиксом `/api/v1`, укажите `/api/v1/chat/completions`. Ключ храните в `MODEL_PRIMARY_API_KEY`. [Open WebUI API](https://docs.openwebui.com/reference/api-endpoints/)

Получите доступные ID и укажите нужный в `MODEL_PRIMARY_ID`. Затем прогоните три синтетических ответа. Команды запускаются из корня проекта в Python-окружении с `requirements.txt`.

```sh
python -m app.ai --list-models
python -m app.ai correct
python -m app.ai partial
python -m app.ai wrong
```

Для локальных тестов установите зависимости через `python -m pip install -r requirements-test.txt` и выполните `python -m unittest discover -s tests`. Чтобы включить интеграционные проверки очереди, Telegram и Mini App, задайте `BILET_TEST_DATABASE_URL` на отдельную тестовую PostgreSQL с миграциями и тестовым курсом.

**Контракт воркера.** Воркер захватывает ключ `grade:{attemptId}` с типом `grade` и JSON `{"attemptId":"…"}`, увеличивает `tries` и передаёт ID и `lease_until` в `app.ai.jobs.handle_grade_job` вместе с подключением к БД без открытой транзакции. Аренда покрывает основной и резервный HTTP-вызовы. Обработчик сохраняет итог и ставит задачу типа `deliver_grade` с полями `attemptId` и `expectedStatus` в одной транзакции. Доставка сверяет статус с текущим результатом попытки.

Временные сбои возвращают задачу в очередь через 15 и 60 секунд с учётом `Retry-After`. После исчерпания попыток результат отмечается `failed`. Повтор по кнопке возвращает то же задание в `queued` и сбрасывает `tries`. Резерв можно задать через `MODEL_FALLBACK_URL`, `MODEL_FALLBACK_ID` и `MODEL_FALLBACK_API_KEY`.

### Импорт учебных материалов

Миграция `004_imports` добавляет записи импорта и распознанные источники. `app.imports.service.create_import` ставит загрузку в очередь от имени активного организатора или преподавателя. Передайте текст или один файл с вопросами и до пяти дополнительных файлов. Для файла используйте `Upload(filename, data)`. Повтор с тем же `Idempotency-Key` и содержимым возвращает прежний ID. Изменённое содержимое с прежним ключом даёт `STATE_CONFLICT`.

Воркер поддерживает TXT (UTF-8), PDF, DOCX, JPEG и PNG. У PDF извлекается текстовый слой. Фото и PDF без текстового слоя распознаются Tesseract с языками русского и английского. Образ Docker уже включает эти пакеты. Для локального Python нужен Tesseract в `PATH` или полный путь в `TESSERACT_BIN`. DOCX читается по абзацам. Лимит страниц проверяется по метаданным и разрывам, если они присутствуют в файле. [PDFium](https://pypdfium2.readthedocs.io/en/stable/python_api.html) · [Tesseract](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)

`app.imports.service.read_import` возвращает статус, черновик вопросов, предупреждения и структурированную ошибку с именем файла и номером страницы, когда они известны. При неоднозначном списке настроенная основная модель предлагает границы вопросов. Воркер сверяет формулировки с исходным текстом. При сбое модели черновик разбивается по строкам с предупреждением.

API и воркер используют общий закрытый том `import_uploads`. Исходные файлы удаляются после обработки. Воркер также удаляет исходники, пролежавшие 24 часа. В БД остаются нормализованный текст и адрес источника. В `sources.pages` лежат записи `{"locator":{"page":1},"text":"…"}` или `{"locator":{"paragraph":1},"text":"…"}`. Загрузка доступна организатору и преподавателю через Mini App.

### Подтверждение вопросов и эталонов

После проверки черновика вызовите `app.rubrics.service.confirm_import(connection, import_id, member_id, idempotency_key, questions)`. Метод принимает отредактированный список с полями `ordinal` и `text`, ставит генерацию в очередь и возвращает `{"status":"generating"}`. Точный повтор запроса возвращает тот же ответ. Заменять весь набор вопросов можно до активации курса.

Воркер делит материалы подтверждённого импорта на фрагменты до 1200 знаков с перекрытием 150 знаков. Полнотекстовый поиск PostgreSQL выбирает для каждого вопроса до пяти фрагментов этого курса. Модель предлагает ответ и 3–5 ключевых пунктов, а код проверяет ID и дословность каждой цитаты. Если часть пунктов осталась без источника, у черновика ставится `sourceStatus=unsourced`. При исчерпании повторов или отсутствии модели создаётся черновик для ручного заполнения. [Полнотекстовый поиск PostgreSQL](https://www.postgresql.org/docs/17/textsearch-controls.html)

- `app.rubrics.service.list_tickets(connection, course_id, member_id)` возвращает свежую версию и отдельно номер утверждённой, если есть.
- `app.rubrics.service.read_source_chunk(connection, chunk_id, member_id)` возвращает текст источника, имя файла и страницу или абзац для редактора.
- `app.rubrics.service.update_rubric` принимает `base_version`, `answer`, `points` и `approve`. Утверждение без полного набора источников требует `acknowledge_unsourced=True`. При устаревшей версии возвращается `STATE_CONFLICT`. Редактирование создаёт новую версию. Уже выданные задания продолжают ссылаться на прежнюю.

Миграция `005_rubrics` добавляет индекс фрагментов и защищает опубликованные версии от правки. Подтверждение импорта, просмотр источников и утверждение эталонов доступны через Mini App.

### Ветки и PR

Возьмите задачу из бэклога и назовите ветку по её ID, например `feat/core-01-schema`. В PR укажите ID, как проверить критерии приёмки и какие контракты изменились. Первую миграцию ведёт владелец CORE. Для интеграции используйте тестовый курс, тестовый Telegram-чат и обезличенные ответы. Реальные токены и ключи задаются через локальное окружение или хранилище секретов стенда.
